# Design

## Context

动机见 `proposal.md` — Why。塑造形态的实测事实：

| 事实 | 值 |
|---|---|
| 两份实现 | `check_project_specs.py:177`（门禁组件用，**0 直接测试**）· `selected_change_closeout.py`（BUG-003 修复引入的并行实现，11 条测试） |
| 语义分歧 | 缩进（无界 vs ≤3 格）· 反引号 info-string（不检查 vs 按规范） |
| 分歧可达性 | 实测：两例旧实现**藏掉 CommonMark 认定的真标题** ⇒ 门禁组件假阴性（BUG-004） |
| `strip` 的既有契约 | **保持行号**（specs checker 按行号报违规，删行会静默移动其后所有行号） |
| 改动后行数 | `check_project_specs` 464 → 445 · `selected_change_closeout` 295 → 257 · 新模块 83 |

## Goals / Non-Goals

**Goals:** 围栏规则只有一处实现且**有规范依据与直接测试** · 门禁不再漏看真标题 · 两处棘轮
同时**下调** · 既有断言与所有门禁不回退。

**Non-Goals:** 不动其他解析器；不拆 257 行的 closeout 工具；不改缩进代码块的"是否算任务"语义。

## Decisions

### D-1｜一个核心 + 三种形态，而不是两个函数各写一遍

- **选**：核心是 `fence_flags(lines) -> list[bool]`（每行是否属围栏，**含开启与闭合行**）；
  `iter_outside_fences` 与 `strip_fenced_code_blocks` 都建在它上面。
- **为什么**：两个调用方需要**不同形状**——closeout 要"围栏外的行"，specs 要"围栏内容换成空行、
  行号不动"。若各写一份，规则又会漂移（这正是本 change 要消除的病）。
- **代价**：`fence_flags` 返回列表（O(n) 内存）而非流式。
- **换来**：`strip` 的行号契约天然成立（一个 flag 对一个 line，一一对应）。

### D-2｜`fence_flags` 把开启与闭合行**也**标记为围栏内

- **选**：True 覆盖开启行、内容行、闭合行。
- **为什么**：`strip` 的既有行为就是这三类都换成空行（原实现的 `output.append("")` 覆盖三者），
  保持它才能保证 specs checker 行为不变。
- **代价**：`iter_outside_fences` 的语义是"不属于任何围栏的行"，围栏定界符也不产出——对 closeout
  工具无影响（它只找 checkbox，定界符不是任务）。
- **换来**：两种形态共享同一份 flag，无二次判定。

### D-3｜缩进取规范值（≤3 格），并显式承认 4 格是缩进代码块

- **选**：`^ {0,3}` 严格；4 格缩进的 ``` **不**开围栏。
- **为什么**：这是 BUG-004 的一半。旧实现的无界 `^\s*` 会把 4 格缩进的 ``` 当围栏，从而**藏掉**
  其后未缩进的真标题——门禁组件的假阴性。
- **代价**：specs checker 的解析**变严格**（这是有意的语义收紧）。
- **换来**：与规范一致；两条回归测试钉住两个原分歧例。

### D-4｜反引号围栏的 info-string 不得含反引号

- **选**：实现 §4.5 的限制（波浪号围栏**没有**该限制）。
- **为什么**：BUG-004 的另一半；且这条限制容易被当成"无关紧要的细节"而在后续重构中丢失，故
  同时用两条测试固定（反引号**受限**、波浪号**不受限**）。
- **换来**：该规则不会被"顺手统一"掉。

### D-5｜棘轮跟着实测值**下调**

- **选**：`check_project_specs` 464 → 445、`selected_change_closeout` 295 → 257。
- **为什么**：体积表的规则是"上限 = 实测值"。删掉本地副本后若保留旧上限，文件就能在无人察觉的
  情况下长回原来的体积——棘轮会失去意义。
- **代价**：两行表项改动。
- **换来**：这次收敛**永久锁定**；同时新模块按其实测值 83 入表。

### D-6｜共享模块按名导入，不加路径守卫

- **选**：`import markdown_fences`；不在调用方加 `sys.path` 操作。
- **为什么**：两种调用方式都已满足——作为脚本运行时，脚本所在目录自动进 `sys.path[0]`；
  治理测试显式插入 `GOVERNANCE_DIR`（`test_project_specs.py` 里就有这段）。不加守卫可避免给
  一个**顶格**文件再加行。
- **代价**：依赖一条隐式约定。
- **换来**：零额外行；约定写进模块 docstring，导入失败时的报错也能自解释。

## Risks / Trade-offs

- [收紧语义改变 specs checker 的判定] → 这正是修复目标；其**自身既有断言**（治理套件内）全绿，
  且两条回归测试明确断言"真标题不再被藏"。
- [共享模块被错误的加载方式导入而失败] → 见 D-6；docstring 写明契约，且现有两种调用方均已验证
  （套件 217 条含 specs 与 closeout 的全部用例）。
- [`fence_flags` 返回列表而非流式] → tasks.md 规模（几百行）下无实际影响；换来两个调用方共享
  同一份判定。
- [棘轮下调后有人直接改表] → 表内注释写明"上限 = 实测值"；且预算测试会比对声明与实测。

## Migration Plan

1. 建共享模块（`fence_flags` / `iter_outside_fences` / `strip_fenced_code_blocks`）。
2. 两个调用方改接、删除本地副本。
3. 写 19 条直接测试（含 BUG-004 两条回归）。
4. 三处变异检查证明守卫能红。
5. 棘轮下调 + 登记新模块。
6. BUG-004 毕业翻转；门禁；归档。

**回滚**：撤销 diff；BUG-004 卡片 `git mv` 回 `bugs/` 并翻回 `修就绪`。
