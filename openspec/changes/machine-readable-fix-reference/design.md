# Design

## Context

动机见 `proposal.md` — Why。塑造形态的实测事实：

| 事实 | 值 |
|---|---|
| 该方面的既有检查 | **零**（全库 grep 零命中） |
| 六张归档卡点名的 change | **全部存在**，但两张卡**同时提到多个** change（发现的那把 vs 修的那把） |
| 状态词表 | 调查中 / 修就绪 / 已落修 / 等人拍板 / 待修 / 已修（`BACKLOG_STATUS_VOCABULARY`） |
| 账本规则落点 | `ledger.py` 的 `_card_hukou_problems` / `_ledger_*` 助手，由 `rules.py` 的 `_rule_ledger_consistency` 编排 |
| 电池清单 | 43 条（31 负例 + 12 绿色），pin 被测试钉死 |

## Goals / Non-Goals

**Goals:** 字段最小且可机械解析 · 六个卡迁移后真实树绿 · "点名不存在的 change"红 ·
进正典电池且 pin 同步 · 既有判定只增不改。

**Non-Goals:** 不做"修复未落地就预填"的推断 · 不覆盖 issues 面 · 不解析正文 · 不动产品代码。

## Decisions

### D-1｜字段是独立的一行引用块：`> 修复: <change-name>`

- **选**：放在状态行之后，形如 `> 修复: fix-closeout-fence-awareness`；正则
  `^> 修复[:：]\s*([a-z0-9][a-z0-9-]*)\s*$`（MULTILINE），**至多一条**。
- **为什么**：既有卡头已经是引用块行（`> 严重级别: … | 发现: … | 状态: …`），同一视觉家族；
  独立成行则正则无需处理"同一行里还有别的字段"的情况（`状态:` 的解析就是这么变复杂的）。
- **代价**：卡片多一行。
- **换来**：解析无歧义；`修复关联` 正文可以继续自由书写（字段负责机器、正文负责人）。

### D-2｜必填集合 = {`已落修`, `已修`}；出现即须有效

- **选**：这两种状态**必须**有该字段；**任何**状态下若出现该字段，点名的 change 必须存在。
- **为什么**：只有这两种状态"修复已落地"，字段才有确定含义。其余状态**既不强制也不禁止**——
  "修复尚未落地就不许预填"是**另一条推断**：一个 `修就绪` 的卡可能已经有提案中的 change，
  禁止它会与"提案先于落地"的常规流程打架。
- **代价**：`调查中` 的卡若预填了不存在的 change 也会被报（那是**好事**：写下的引用要真）。
- **换来**：判据最小且无推断。

### D-3｜存在性判定：活跃目录名 或 归档目录的日期前缀名

- **选**：`openspec/changes/<name>` 存在，**或** `openspec/changes/archive/<YYYY-MM-DD>-<name>` 存在。
- **为什么**：本仓归档会把目录重命名为 `日期-名字`（证据：94 个归档目录全为该形态）。卡片写在
  归档之后，点名的自然是当时的名字。
- **代价**：需要两次存在性判断。
- **换来**：已修卡（其 change 必然已归档）与在修卡（change 仍活跃）用同一字段。

### D-4｜落在 `doc-hygiene` 的账本规则里，并进正典电池

- **选**：新增 `_card_fix_reference_problems(scope, root)`，由 `_rule_ledger_consistency` 调用；
  同时在 `doc_hygiene_battery` 加 1 负例（点名不存在 → 必须报）+ 1 绿色（有效引用 → 不报），
  pin 31/12/43 → **32/13/45**。
- **为什么**：账本规则的 owner 就是 doc-hygiene；而"新守卫必须能变红"在本仓的落点就是电池——
  加进电池后，`failing_controls()` 直接给出变异证明，不必另写一套测试。
- **代价**：pin 与电池文档注释同步更新。
- **换来**：守卫进正典清单，且"能红"有现成机制证明。

### D-5｜字段写进卡格式的声明处

- **选**：把新字段写进 `_backlog/bugs/README.md` 的卡片模板（以及 `_backlog/README.md` 若那里
  也描述卡格式）。
- **为什么**：格式的定义处不写，后来者只会在 doc-hygiene 的报错里发现它——那是"守卫比文档先知道"
  的倒挂。
- **换来**：文档与守卫同源。

## Risks / Trade-offs

- [迁移 6 张卡时把"发现它的 change"误当成"修它的 change"] → 提案里的对照表逐卡核实过（BUG-003 是
  `fix-closeout-fence-awareness` 而非 `cover-closeout-decisions`；BUG-005 是
  `doc-hygiene-adopts-fence-rule` 而非 `share-fence-parsing`）。
- [存在性判定漏掉活跃 change] → D-3 两个分支都判；负例只覆盖"两处都不存在"。
- [电池 pin 忘改] → 清单测试会红（本会话已多次由它抓出）。
- [字段与正文冲突] → 本把**不**校验正文与字段一致（那需要解析自由文本，正是本把要摆脱的）；字段
  是权威，正文是叙述——写进 D-1 的说明。
- [文件变大触闸] → 按实测重测。

## Migration Plan

1. 六张卡补字段（值取提案对照表）。
2. `constants.py` 加字段正则与必填状态集。
3. `ledger.py` 加助手 + 由 `_rule_ledger_consistency` 调用。
4. 电池 2 条控制 + pin；卡格式文档补字段。
5. 体积表按实测；门禁；收口。

**回滚**：撤销 diff（字段行删除、助手与常量删除、电池控制与 pin 回退）。
