# Design

## Context

动机见 `proposal.md` — Why。塑造形态的实测事实：

| 事实 | 值 |
|---|---|
| 该模式的测试覆盖 | **零**（`openspec/tests/**` 里 3 处 `## Program Focus` 全是别的规则的围栏夹具） |
| 真实用户 | 1 个（`2026-10-07-surface-runtime-structure`，3 个工作流） |
| 实现规模 | 约 99 行 / 6 模块 |
| `program.*` 违规码 | 见代码清单；本把覆盖 4 个 + 正典绿例 |
| 我写合规夹具的代价 | **三次迭代**（见偏差 1）——这本身就是"零覆盖"的实证 |

## Goals / Non-Goals

**Goals:** 给被保留的模式补**正典用例**（绿例证明合规 program 能通过 + 四条红例各自指名违规码）·
**实现零改动** · 用例**承重**（变异能红）。

**Non-Goals:** 改实现或语义 · 覆盖整条端到端链路 · 覆盖该模式的每一个违规码 · 产品代码。

## Decisions

### D-1｜直接调 `_validate_program_proposal`，不搭整棵 change 树

- **选**：与该测试文件**既有风格**一致——直接调校验函数、断言 `ContractViolation.code`。
- **为什么**：这条路径的输入就是一个 proposal 文本 + 路径；搭整棵树（config/规格/其他节）会引入
  与本把无关的失败面（例如 config 路由、Focus Card 互斥），让红例**指错因**。
- **代价**：**不覆盖调用方那层**（工作流级 review 小节的校验在调用方）。已写进 docstring 与
  Not in scope——宁可有边界的覆盖，也不要含糊的"覆盖了"。
- **换来**：每条用例的失败都精确指向被测函数的一个分支。

### D-2｜绿例是重点，不是红例

- **选**：先写一个**合规**的 program 提案并让它通过。
- **为什么**：这个模式的意义就是"合规的多工作流 program 能被受理"；没有绿例时，四条红例只能证明
  "它会拒绝"，证明不了"它能受理"。**一个只会拒绝的校验器和一段没人用的代码一样糟。**
- **代价**：写合规夹具要满足全部约束（我为此迭代三次）。
- **换来**：该模式首次有了"能被正确使用"的证据。

### D-3｜实现零改动是硬指标

- **选**：`git diff --stat -- openspec/governance/change_guidance_check/` 必须为 **0 行**。
- **为什么**：本把是**补覆盖**，不是修实现。若为了"让测试通过"去动实现，那是在改被测对象——
  本仓的铁律（改测试即判失败的反向版本）。
- **换来**：结论干净——"这段代码本来就能工作，只是没人验证过"。

## Risks / Trade-offs

- [夹具与真实用法漂移] → 夹具的字段集直接来自 `PROGRAM_FOCUS_FIELDS` / `WORKSTREAM_FIELDS`
  常量；迭代中暴露的三条隐含约束已写进偏差记录。
- [红例指错因] → D-1 的直接调用；且每条红例断言的是**具体 code**。
- [只覆盖 4/若干违规码被读成"全覆盖"] → Delivery Record 的未执行检查里写明覆盖面。
- [测试变成"实现是什么就断言什么"] → 变异检查证明用例承重（下限 2→3 ⇒ 3 条用例失败）。

## Migration Plan

1. 在既有测试文件里加 `ProgramModeTests` + 两个夹具构造函数。
2. 迭代到绿例通过（过程中暴露三条约束，记入偏差）。
3. 变异检查；全套门禁；收口。

**回滚**：撤销 diff（删掉测试类与夹具，实现本来就未动）。
